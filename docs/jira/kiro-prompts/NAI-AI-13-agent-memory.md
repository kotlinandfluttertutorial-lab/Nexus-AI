## Architecture Rules

- Memory access is mediated by a `MemoryRepository` interface in the domain layer.
- Implementation (SQLite, Redis, or in-memory) lives in `infrastructure/` — not domain.
- `MemoryRepository` is injected into the agent — agents never access storage directly.
- Session memory is keyed by `session_id` — no cross-session leakage.
- Conversation content is never logged at INFO level or above.
- Retention policy is enforced by the repository on every write (max turns or max age).

## Implementation Task

### 1. Memory Domain Interface

Create `backend/agent-runtime/memory/interface.py`:

```python
class MemoryRepository(Protocol):
    async def add_message(self, session_id: str, role: str, content: str) -> None: ...
    async def get_history(self, session_id: str, last_n: int = 20) -> list[Message]: ...
    async def search_relevant(self, session_id: str, query: str, top_k: int = 5) -> list[Message]: ...
    async def clear(self, session_id: str) -> None: ...
    async def delete_session(self, session_id: str) -> None: ...
```

### 2. In-Memory Implementation

Create `backend/agent-runtime/memory/in_memory_store.py`:
- `dict[session_id, list[Message]]` backing store
- `get_history()` returns last `last_n` messages
- `search_relevant()` does simple keyword overlap (upgrade to vector search in AC4)
- Enforces `max_turns` retention policy on every `add_message()`

### 3. Persistent Implementation

Create `backend/agent-runtime/memory/sqlite_store.py`:
- SQLite database at a configured path
- Schema: `sessions(session_id, created_at)` + `messages(id, session_id, role, content, timestamp)`
- Migrations applied on startup via a `create_tables()` call
- `search_relevant()` uses vector similarity via the `VectorStore` from NAI-AI-15 if available,
  otherwise falls back to recency-ordered results

### 4. Retention Policy

Both implementations enforce on every `add_message()`:
- `max_turns: int` — delete oldest messages if count exceeds limit (default: 100)
- Retention settings configurable from environment: `MEMORY_MAX_TURNS`

### 5. FastAPI Integration

Add memory endpoints to `backend/fastapi-service/api/routers/memory.py`:
- `GET /v1/memory/{session_id}` — return session history
- `DELETE /v1/memory/{session_id}` — clear session
- Wire `MemoryRepository` into `AgentExecutor` via `Depends`

### 6. Demo

Create `learning/13-agent-memory/memory_demo.py`:
- Creates a session, sends 5 messages, retrieves history, searches for a relevant message,
  clears the session, confirms empty

## Acceptance Criteria

| # | Criterion |
|---|---|
| AC1 | Session memory stores messages per `session_id` without cross-session leakage. |
| AC2 | Conversation memory persists across process restart (SQLite implementation). |
| AC3 | `get_history()` returns messages in chronological order. |
| AC4 | `search_relevant()` returns messages semantically related to the query (keyword or vector). |
| AC5 | `clear()` removes all messages for a session; subsequent `get_history()` returns empty. |
| AC6 | Retention policy deletes oldest messages when `max_turns` is exceeded. |
| AC7 | `MemoryRepository` is a domain interface; implementation lives in `infrastructure/`. |
| AC8 | Tests cover: add, get_history, search_relevant, clear, and retention boundary conditions. |
