## Target Architecture

```
UI
↓
AI Orchestration
↓
AI Provider Interface  (Domain)
↓
Provider Implementation  (Data — Gemini, OpenAI, On-device, etc.)
```

**Provider-specific SDK models must not appear in Domain or Presentation code.**

## Implementation Task

Establish provider-independent abstractions:

- `AIProvider` interface
- `AIStreamClient` interface
- `AIRequest` model (messages, tools, config)
- `AIResponse` model
- `AIStreamEvent` sealed type:
  - `Started`
  - `Token`
  - `ToolCall`
  - `ToolResult`
  - `Completed`
  - `Error`
- `AIError` sealed hierarchy
- At least one concrete provider implementation
- `FakeAIProvider` for testing

## Acceptance Criteria

| # | Criterion |
|---|---|
| AC1 | Provider-independent AI interfaces exist in Domain. |
| AC2 | AI request/response models are defined. |
| AC3 | Streaming events are standardized via `AIStreamEvent`. |
| AC4 | Provider-specific models remain isolated inside provider implementations. |
| AC5 | At least one AI provider is integrated. |
| AC6 | Provider errors are mapped to the `AIError` hierarchy consistently. |
| AC7 | `FakeAIProvider` exists and can be used in tests. |

## Test Requirements

- Interface contract tests
- Request/response mapping tests
- Streaming event tests (all event types)
- Error mapping tests (all `AIError` subtypes)
- `FakeAIProvider` tests
- Provider integration tests using controlled/fake data
- Build validation

> Do not place provider SDK dependencies directly in feature UI or Domain.
